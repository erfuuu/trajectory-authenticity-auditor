# TraceAudit

一个面向软件代理 JSONL 轨迹的结果与过程质量审核工作台。批量上传轨迹文件后，TraceAudit 会先在本地完成确定性结构检查，再逐份串行调用 GPT 模型核对用户需求、执行证据、因果链、修改与验证过程，最终生成九维质量评分、重大瑕疵、结果结论和改进建议。

> 当前版本处于实验阶段。报告用于辅助人工审核，不构成密码学意义上的真实性证明。

## 功能

- 批量拖拽上传 `.jsonl` 或 `.json` 轨迹文件
- 按文件串行机审，避免多份轨迹共享模型上下文
- 单份失败不阻断后续队列，支持保留失败任务重试
- 在浏览器本地管理历史机审结果
- 按轮次解析并展示轨迹中的外部用户 Prompt
- 本地解析 JSONL，不依赖模型计算结构指标
- 检查工具调用与结果配对、事件父链、重复 ID 和时间顺序
- 为输入文件计算 SHA-256
- 识别用户验证、构建结果和代理成功声明
- 使用 `gpt-5.4-mini` 生成九维结果与过程质量评分
- 每项评分包含原因、引用证据、扣分项和补证建议
- 单独判断交付结果是已证实成功、部分证实、未证实、已证实失败或无法判定
- 标出影响正确性、明确约束、安全边界或可验收性的重大瑕疵
- 输出未充分支持的声明与用户验证结论
- 支持下载 JSON 报告和浏览器打印
- 支持 OpenAI 官方接口及 Responses API 兼容中转站
- API Key 仅保存在当前浏览器会话，不写入服务端文件

## 工作流程

```text
JSONL 轨迹
    │
    ├── 本地确定性检查
    │   ├── JSON 解析与事件统计
    │   ├── tool_use / tool_result 配对
    │   ├── UUID、parentUuid 与时间顺序
    │   └── SHA-256 与结构分
    │
    └── 高优先级证据抽取
        ├── 用户实际验证
        ├── 错误与构建结果
        ├── 成功声明
        └── 关键工具操作
              │
              ▼
       GPT-5.4-mini 质量审核
              │
              ▼
       结果结论 + 九维评分 + 重大瑕疵
```

原始轨迹不会被整体直接塞进模型上下文。本地分析保留完整结构事实，模型只接收经过排序和截断的证据包。

## 审核维度

| 维度 | 权重 | 审核内容 |
| --- | ---: | --- |
| 交付完整性 | 18% | 功能点是否完整，代码能否运行，有无虚假成功 |
| 用户体验 | 8% | 交互是否简洁及时，有无冗长废话或过度报告 |
| 指令遵循 | 14% | 是否逐项满足 Prompt 中的明确要求与约束 |
| 任务规划 | 10% | 拆解、状态追踪、必要澄清和阶段反馈是否合理 |
| 推理能力 | 14% | 是否先读上下文、基于证据定位根因并闭环修复 |
| 边界感 | 8% | 是否尊重架构、工作区和危险操作授权边界 |
| 修改质量 | 10% | 修改范围、契约一致性和可维护性是否合格 |
| 验证质量 | 12% | 验证是否覆盖改动、可归因，必要时是否有 E2E |
| 工具与效率 | 6% | 工具选择是否合理，有无重复劳动或无意义调用 |

综合分为九个维度的加权平均值。存在重大瑕疵、综合分低于 70，或交付完整性、指令遵循、验证质量任一低于 60 时，整体判定不会高于“存在重大瑕疵”。

### 证据等级

| 等级 | 含义 |
| --- | --- |
| E0 | 模型或代理文字声称完成 |
| E1 | `Write` / `Edit` 返回成功 |
| E2 | 后续读取与修改内容一致 |
| E3 | 编译、构建或自动化测试通过 |
| E4 | 实际启动、接口调用或端到端功能验证 |
| E5 | 用户、CI 或外部系统独立验证 |
| E6 | 数字签名、可信时间戳、哈希链和外部存证 |

`Write` 成功只证明发生了写入，`BUILD SUCCESS` 只证明编译成功。TraceAudit 不会把这些信号直接解释为功能已经可用。

## 上下文与超时控制

TraceAudit 可以一次将多个轨迹加入队列，但每个模型请求仍只审核一个轨迹文件。队列严格串行执行，每份轨迹独立采用自适应证据窗口：

1. 首次模型请求最多携带约 24,000 个字符的高优先级证据。
2. 如果上游返回 `504` 或超时，自动缩减到约 12,000 个字符重试。
3. 用户反馈、失败结果、构建日志和成功声明优先保留。
4. 完整事件数、调用配对、哈希和结构异常始终由本地程序计算，不受证据窗口影响。
5. 模型固定使用低推理强度，以降低中转网关超时和调用成本。

这种方式优先保证日常审核稳定性。需要深度取证时，建议结合原始轨迹、外部 CI 日志和产物重放进行人工复核。

## 快速开始

### 环境要求

- Node.js 20 或更高版本
- OpenAI API Key，或兼容 Responses API 的服务
- 现代浏览器

项目仅使用 Node.js 内置模块，没有运行时 npm 依赖。

### 启动

```bash
git clone https://github.com/erfuuu/trajectory-authenticity-auditor.git
cd trajectory-authenticity-auditor
npm start
```

浏览器访问：

```text
http://127.0.0.1:4173
```

使用其他端口：

```bash
PORT=8080 npm start
```

### 运行测试

```bash
npm test
```

## API 配置

打开页面右上角的“API 设置”。

### OpenAI 官方接口

```text
API Base URL: https://api.openai.com/v1
模型: gpt-5.4-mini
```

### Responses API 兼容中转站

填写中转站提供的 Base URL，不要填写具体的 `/responses` 路径。例如中转站要求：

```text
https://example-provider.com
```

服务端会请求：

```text
https://example-provider.com/responses
```

如果中转站使用 `/v1` 前缀，则填写：

```text
https://example-provider.com/v1
```

模型名称必须是该服务实际支持的模型 ID。页面默认使用 `gpt-5.4-mini`，也可以填写自定义模型名称。

## 隐私与安全

- API Key 保存在浏览器 `sessionStorage`，关闭标签页或浏览器会话后失效。
- 历史机审报告保存在浏览器 IndexedDB，可以在页面中单独删除或全部清空。
- 历史记录不保存原始轨迹文件或 API Key，但会保存报告引用的统计信息和解析后的 Prompt。
- API Key 随单次审核请求发送给本机 Node.js 服务，服务端不写入文件，也不会输出到日志。
- 轨迹先在本地服务中解析，但精选证据会发送给配置的模型提供方。
- 使用中转站意味着 API Key 和轨迹证据会经过第三方服务，请确认其隐私政策和可信程度。
- 浏览器页面通过 CSP 限制外部脚本和网络连接。
- 建议使用权限受限、可轮换且设置额度上限的 API Key。
- 不要将 API Key、真实轨迹或生成报告提交到 Git 仓库。

## 支持的轨迹结构

当前版本内置三种适配器：

- Claude Code 风格的 `user` / `assistant`、`tool_use` / `tool_result` 轨迹
- Codex CLI 会话 rollout 的 `session_meta` / `response_item` JSONL
- `codex exec --json` 输出的 `thread.*` / `turn.*` / `item.*` JSONL

解析器会在预检中显示识别到的格式。无法识别的事件不会被伪装成已支持；报告会显示兼容性警告和未适配事件数量。

Claude Code 适配器主要读取以下字段：

- `type`
- `uuid` / `parentUuid`
- `timestamp`
- `sessionId`
- `message.content`
- `tool_use.id`
- `tool_result.tool_use_id`

Codex rollout 适配器会把 `message`、`agent_message`、`reasoning`、`function_call`、`function_call_output` 和本地 Shell 调用规范化为统一证据。`codex exec --json` 适配器会配对命令、文件修改和常见工具项的开始/完成事件。

## HTTP 接口

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/preflight` | 本地确定性结构检查 |
| `POST` | `/api/audit` | 结构检查、证据抽取和模型审核 |

`/api/audit` 通过 `X-OpenAI-API-Key` 请求头接收当前会话的 API Key。

## 已知限制

- 只能证明轨迹内部一致性和证据充分程度，不能单独证明日志未被事后伪造。
- 当前不重放文件修改，也不启动轨迹中的目标项目。
- `codex exec --json` 通常不包含完整初始 Prompt；缺少用户原始约束时，指令遵循维度只能判为证据不足。需要完整审核时优先使用 Codex 会话 rollout。
- Codex CLI 的事件结构可能随版本扩展；预检出现“部分支持”时应先补充对应事件适配器。
- 用户验证识别包含启发式规则，可能出现误判或漏判。
- 模型评分具有一定随机性，不应作为唯一处罚或验收依据。
- 超长轨迹会截断低优先级证据，报告中会记录包含和省略的证据片段数量。
- 某些中转站不完整支持 Responses API、结构化输出或长请求。
